# ADR-0014. Чужой API не бывает несущим

**Статус:** Принято, 2026-08-24.

## Контекст

В проекте six-feat интегрировали Яндекс.Музыку. Официального API у неё нет —
есть реверс-инженеренные библиотеки, у которых перед нами нет никаких
обязательств: ни совместимости, ни сроков, ни ответа на вопрос «почему
перестало».

Интеграцию сделали **несущей**: она стала обязательным источником данных.
Сущности продукта завели на чужих идентификаторах, таблицы — на чужой модели,
сценарии — на предположении, что ответ придёт.

Когда выяснилось, что нужного через неё не получить, удаление стоило **182
файла и +6640/−5002 строки**. Снесло сервис, библиотеку, таблицу в схеме и
половину продуктового релиза.

Это не невезение. Библиотека не сломалась и API не закрыли — просто оказалось,
что данных, ради которых всё затевалось, там нет. Дорогим удаление сделало не
это, а решение сделать чужой нестабильный API несущим и разложить его
идентификаторы по своим таблицам.

У нас снаружи будет: платёжный провайдер, чеки самозанятого, LiveKit, провайдер
моделей и эмбеддингов, календари, распознавание текста. Ни один из них не наш.

## Решение

**Внешний API — украшение. Несущим он не бывает.**

Шесть правил, и они не про вкус, а про счёт удаления:

1. **Неофициальный и реверс-инженеренный API не бывает несущим никогда.**
   Официальный, с публичными обязательствами по совместимости, — может нести
   функцию, которую без него не сделать. Всё остальное — только украшение,
   отключаемое без последствий.
2. **Каждый внешний API за портом, реализаций минимум две:** настоящая и
   заглушка. Одна реализация означает, что порт списан с этого API, и второй
   провайдер в него не влезет.
3. **Деградация обязательна и проверяется.** У каждой интеграции есть прогон
   «внешнего сервиса нет НАВСЕГДА»: продукт работает, функция отсутствует,
   человек видит понятное объяснение. Не «вернул ошибку» — ошибку обрабатывают
   и идут дальше; «его нет и не будет» — это другой вопрос, и отвечает на него
   другой тест.
4. **План удаления пишется ДО интеграции.** В ADR каждой интеграции —
   раздел «Как это выключить»: какие таблицы осиротеют, какие функции исчезнут,
   сколько файлов затронуто. **Если ответ «неизвестно» — интеграцию делать
   рано.**
5. **Чужие данные не становятся нашими идентификаторами.** Внешний
   идентификатор живёт в таблице соответствия, а не первичным ключом наших
   сущностей. Именно это сделало удаление в six-feat дорогим: чужой ключ
   прорастает в каждый запрос и в каждый внешний ключ.
6. **Отключение — флаг в динамическом конфиге** (`PDR-CFG-01`), а не правка
   кода. Интеграция, которую выключают выкаткой, не выключается в тот момент,
   когда это нужно.

Реестр интеграций и проверка — [integrations.md](../architecture/integrations.md).
Шаблон ADR интеграции — [TEMPLATE-integration.md](TEMPLATE-integration.md).

## Последствия

* **Продукт беднее.** Функция, которую нельзя сделать без чужого API, либо не
  делается, либо делается как украшение — с честным «сейчас недоступно» на
  экране. Это цена, и она осознанная;
* **работы больше на каждой интеграции**: порт, две реализации, прогон
  деградации, раздел «как выключить», запись в реестре, флаг в конфиге. Это
  примерно день на интеграцию — против ста восьмидесяти двух файлов;
* **таблица соответствия — лишний join.** Чужой идентификатор в отдельной
  таблице стоит перехода при каждом обращении. Взамен удаление интеграции
  сносит одну таблицу, а не переписывает схему;
* **некоторые API отпадают сразу.** Реверс-инженеренный источник не может
  нести функцию, а значит, ради него не стоит и заводиться, если украшением он
  бессмыслен. Это правильный отсев, и он происходит до кода, а не после.

## Альтернативы и почему отвергнуты

**Решать в каждом случае отдельно, по здравому смыслу.** Именно так и решали в
six-feat: интеграция выглядела безобидной, пока не стала несущей — это
произошло не решением, а постепенно, за несколько задач. Правило нужно ровно
потому, что момент превращения не виден изнутри.

**Разрешить несущие интеграции с официальным API и не различать остальные.**
Отвергнуто: различие между «есть обязательства» и «работает, пока работает» —
единственное, что вообще можно проверить заранее. Стереть его значит вернуться
к «решаем по ситуации».

**Абстрагировать любой внешний API «на всякий случай» и этим ограничиться.**
Порт защищает от смены провайдера, но не от того, что случилось: продукт всё
равно перестаёт работать, когда за портом никого. Без прогона деградации порт —
это место, где ошибка красиво заворачивается, и только.

**Писать план удаления, когда удаление понадобится.** Отвергнуто: в этот момент
интеграция уже проросла, и план пишется по факту раскопок. Вопрос «сколько
файлов затронет удаление» дёшев ровно один раз — до того, как их стало сто
восемьдесят два.

**Флаг сборки вместо флага в конфиге.** Отвергнуто: выключение выкаткой
означает, что между «стало ясно, что надо выключить» и «выключено» лежит
релизный цикл. Внешние сервисы ломаются не по расписанию релизов.
