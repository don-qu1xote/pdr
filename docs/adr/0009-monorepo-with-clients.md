# ADR-0009. Монорепозиторий с несколькими клиентами

**Статус:** Принято, 2026-08-19.

## Контекст

Клиент сейчас один — веб. Мобильные приложения — принятое продолжение проекта,
а не гипотеза: репетитор смотрит расписание с телефона, ученик открывает задание
с телефона, напоминание приходит push-уведомлением.

Клиенты делят между собой две вещи, и обе меняются часто:

* **типы, сгенерированные из OpenAPI** — контракт с бэкендом;
* **значения системы дизайна** — `clients/shared/design/tokens.json`,
  единственный источник цветов, кеглей, отступов и радиусов.

Вопрос «а не вынести ли мобильный клиент в свой репозиторий» будет всплывать
каждый раз, когда репозиторий покажется большим.

## Решение

Один репозиторий: `clients/web`, `clients/mobile`, `clients/shared`.

Каталог `clients/` назван во множественном числе с самого первого коммита
именно поэтому: переименовывать `front/` в `clients/web/` на живой истории
дороже, чем назвать сразу.

`clients/mobile` в дереве пока нет — он появится вместе с мобильным клиентом.
Пустой каталог про запас мы не заводим: это то же правило, по которому не
заводятся пустые модули контекстов.

## Последствия

* изменение схемы API и изменение всех клиентов под неё — **один коммит**.
  Схема и её потребители не могут разъехаться, потому что живут в одной
  истории;
* репозиторий больше, и **сборка в CI обязана собирать только изменившееся**.
  Пока клиентов нет, это условие ничего не стоит; когда их станет двое, сборка
  веба не должна ждать сборки мобильного;
* общий инструментарий: один `.editorconfig`, один формат коммитов, один
  `git log` на весь продукт. Идентификатор задачи связывает изменение бэкенда с
  изменением клиента;
* проверки границ должны понимать, что клиенты — не бэкенд, и не пытаться
  применять к ним правила слоёв.

## Альтернативы и почему отвергнуты

**Репозиторий на клиента плюс пакет с общими типами и токенами.** Отвергнуто:
каждое изменение схемы превращается в версионирование и публикацию пакета, а
затем в обновление зависимости в каждом клиенте. Между этими шагами клиенты
живут на разных версиях API — не потому, что кто-то ленив, а потому, что так
устроен процесс. Для двух клиентов и одного разработчика это чистые издержки.

Этот вариант оправдан, когда у клиентов независимые команды и независимые
релизные циклы: тогда пакет — не издержка, а граница ответственности. У нас
таких команд и циклов нет, и не предвидится в обозримых фазах.

**Общий код через git submodule.** Отвергнуто: половина боли пакета (нужно
помнить про обновление указателя) плюс собственная боль submodule — забытый
`--recursive`, разъехавшиеся указатели, конфликты в файле ссылки.

**Копировать типы и токены в каждый клиент руками.** Отвергнуто: расхождение
наступает не «если», а «когда», и обнаруживается на экране у человека. Кроме
того, это прямо нарушает правило проекта: значения дизайна берутся **только**
из `clients/shared/design/tokens.json`.

**Держать бэкенд и клиенты в разных репозиториях.** Отвергнуто по той же
причине, что и клиенты между собой: OpenAPI — общий контракт, и его изменение
должно быть одним изменением, а не тремя согласованными.
