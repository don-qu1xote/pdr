# Одиночные фоновые задания

**Ровно один воркер во всём кластере делает периодическую работу.** Рассылка
напоминаний, пересчёт горизонта расписания, сверка платежей, уборка старых
следов. Решение и отвергнутые варианты —
[ADR-0011](../adr/0011-single-jobs-on-distlock.md).

Это НЕ очередь. Очередь — «много воркеров разбирают много работ», и она делается
`SELECT ... FOR UPDATE SKIP LOCKED` (`notifications_outbox`,
`ml_inference_job`). Здесь единица работы не строка в таблице, а «наступило
время»: брать нечего, пока кто-то не решит, что пора. Если решат двое, работа
будет сделана дважды.

## Из чего собран механизм

| Часть | Чем сделана | Кто написал |
| --- | --- | --- |
| блокировка | `dist_lock::DistLockedWorker` + `storages::postgres::DistLockStrategy`, строка в `jobs_lock` | userver |
| периодичность | цикл под блокировкой и `engine::InterruptibleSleepFor` | мы |
| настройки | динамический конфиг `PDR_PERIODIC_JOBS` | userver + мы |
| идемпотентность | первичный ключ `jobs_effect (tenant_id, job, effect_key)` | схема |
| журнал и метрика | `jobs_run` плюс `utils::statistics` и `utils::PeriodicTask` | userver + мы |

Своей блокировки в проекте нет ни строчки. `update ... set locked = true`
ломается на перезапуске: строка остаётся занятой умершим воркером, и снять её
некому. У штатной блокировки срок живёт в базе — воркер, перестав его продлевать,
теряет блокировку сам, без чьего-либо участия.

## Что пишет контекст

Ровно два метода, `contract/jobs/contract.hpp`:

```cpp
std::vector<WorkItem> Plan(core::Instant now);  // что нужно сделать
void Perform(const WorkItem& item);             // сделать одну единицу
```

`WorkItem` — это арендатор и **детерминированный ключ действия**. Одна и та же
работа обязана давать один и тот же ключ у любого воркера и в любом прогоне:
«напомнить о занятии `7f3c…` за час до начала» — один ключ, сколько бы раз
задание ни просыпалось.

**Ключ, в который подмешано «сейчас», — не ключ.** Он новый на каждом прогоне, и
идемпотентности не будет вовсе. Это единственное требование, которое механизм не
может проверить за автора задания.

Планирование обязано быть чистым: побочное действие в `Plan` произойдёт и у того
воркера, который подхватил работу после потери блокировки, — то есть дважды.

## Как получается «ровно один раз»

Порядок в `RunPeriodicJob::Execute` (`libs/pdr-jobs/src/jobs/application/`):

1. записать начало попытки в журнал;
2. для каждой единицы плана: спросить блокировку — ещё наша? Проверить, что не
   вышло отведённое на прогон время;
3. поставить след в `jobs_effect`. Не поставился — след уже стоял, действие
   пропускается, счётчик `repeated` растёт;
4. поставился — произвести действие;
5. записать итог: длительность, исход, счётчики.

След ставится ДО действия. Значит, процесс, упавший между следом и действием,
действие потеряет. Выбор осознанный: вторая рассылка ученику и второе списание
денег дороже несостоявшегося напоминания, которое подхватит следующий прогон.

## Настройки: ни одного числа в коде

Динамический конфиг `PDR_PERIODIC_JOBS` — словарь по имени компонента задания:

```json
{
  "notifications-reminders": {
    "lock": "notifications.reminders",
    "period_ms": 60000,
    "attempt_ms": 30000,
    "silence_allowed_ms": 3600000,
    "enabled": true
  }
}
```

| Ключ | Что значит |
| --- | --- |
| `lock` | имя строки в `jobs_lock`; оно же метка в метрике |
| `period_ms` | как часто задание просыпается |
| `attempt_ms` | сколько отведено одному прогону; он же срок жизни блокировки |
| `silence_allowed_ms` | после какого молчания задание считается замолчавшим |
| `enabled` | выключенное задание блокировку не берёт вовсе |

Проверки — доменные, в `jobs::JobSettings`: период положительный, прогон
положительный и не длиннее периода (иначе прогоны наедут друг на друга),
допустимое молчание не короче периода (иначе тревога на каждом прогоне).

**Умолчаний нет.** У переменной целиком умолчание одно — пустой словарь; у
отдельного задания никакого. Задания, которого нет в конфиге, для механизма не
существует: сервис не поднимется и скажет, какого задания не хватает. Значение по
умолчанию у периода означало бы, что забытая настройка выглядит как работающее
задание.

## Метрика: задание, молчащее сутки, видно

Метрики пишутся под префиксом `jobs` с меткой `job`:

| Метрика | О чём |
| --- | --- |
| `silence-ms` | сколько прошло с конца последнего завершённого прогона |
| `duration-ms` | сколько занял последний прогон |
| `produced`, `repeated` | сколько действий произведено и сколько пропущено как уже сделанные |
| `ran` | отрабатывало ли задание вообще |
| `silent` | молчит дольше допустимого (у выключенного задания — ноль) |
| `lock.*` | штатная метрика распределённой блокировки, как её пишет userver |

Журнал `jobs_run` общий на кластер, и это не мелочь: работу делает один процесс,
а показывать возраст последнего прогона обязан каждый. Поэтому на каждом процессе
идёт штатный `utils::PeriodicTask`, который перечитывает настройки, отдаёт их
воркеру и обновляет метрику, — независимо от того, держит этот процесс блокировку
или нет.

Незакрытый прогон записью о прогоне не считается: воркер, упавший посреди
работы, выглядит замолчавшим заданием, а не отработавшим только что.

## Что проверяется и чем

Без базы, за миллисекунды (`make test-unit`, уровень UNIT из
[testing.md](testing.md)):

* повтор прогона не производит ни одного действия второй раз, а `repeated`
  растёт;
* воркер, потерявший блокировку посреди работы, прекращает прогон; второй
  подхватывает и доделывает остаток — каждое действие произведено ровно один раз;
* воркер без блокировки не делает ничего;
* прогон, не уложившийся в отведённое время, прекращается сам;
* возраст последнего прогона растёт, пока воркер стоит; не отрабатывавшее ни
  разу задание считается замолчавшим;
* одинаковый ключ у разных арендаторов — две разные работы, и обе состоятся.

На живой базе (`make test-jobs`, в CI рядом с `make test-isolation`):

* двое на одной блокировке — работает один;
* умерший воркер не держит блокировку вечно: она уходит по сроку;
* чужую блокировку не отпустить;
* след не поставить дважды даже ОДНОВРЕМЕННО: вторая сессия ждёт первую и
  получает конфликт. Этого нельзя проверить на фейках — одновременность бывает
  только в базе;
* след принадлежит арендатору (RLS) и не переписывается: прав на `update` у
  приложения нет;
* журнал помнит последний завершённый прогон и его длительность, а начало новой
  попытки его не затирает;
* возраст последнего запуска растёт при стоящем воркере, и задание, молчащее
  сутки, находится запросом.

## Чего в дереве пока нет

Написано честно, чтобы никто не рассчитывал на несуществующее:

* **сервиса, который крутит задания, нет** — `services/` пуст. Компонент
  `jobs::PeriodicJobComponentBase` написан и разобран компилятором вместе с
  остальными адаптерами, но первый живой прогон случится вместе с первым
  сервисом;
* **ни одного настоящего задания нет.** Ни рассылки напоминаний, ни сверки
  платежей: `notifications_outbox` и таблиц расписания в схеме ещё нет.
  Механизм заведён раньше заданий намеренно — иначе первое же задание принесло
  бы свою блокировку;
* **уборки `jobs_effect` нет.** Индекс по `produced_at` для неё в схеме есть,
  само задание — за первым сервисом;
* **обновлятора динамического конфига нет** (`PDR-CFG-01`): адаптер читает
  `dynamic_config::Source`, а кто и откуда её наполняет, решает та задача.
