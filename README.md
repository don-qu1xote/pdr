# ПДР

Платформа для репетиторов и их учеников.

**Два имени, и это не путаница, а правило.** Снаружи продукт называется
**«Поля»**: сайт, приложение, письма, документы — всё, что видит человек.
Внутри всё остаётся **ПДР**: имя репозитория, префикс задач `PDR-AREA-NN`,
формат коммитов, каталоги, модули, таблицы, конфиги и ADR. Ничего внутреннего
не переименовывается, ничего внешнего не подписывается «ПДР». «ПДР» в тексте
интерфейса и «Поля» в имени модуля — обе ошибки.

## Для кого

Репетитор, ученик, родитель или опекун, самостоятельный взрослый ученик —
у последнего (языки, подготовка в вуз) опекуна нет вовсе, и это не частный
случай, а полноценная роль.

Рынок российский: платежи через ЮKassa за портом, чеки самозанятого
обязательны.

Задуманные подсистемы: расписание, оплаты, видеозанятие, методические
материалы и учебные планы, конспекты уроков, трекинг прогресса, подбор задач,
подбор репетиторов, чаты. Ни одна из них ещё не написана — см. следующий
раздел.

## Что здесь есть прямо сейчас

Дерево каталогов, инструментальные файлы (`PDR-DOC-01`), соглашения работы
(`PDR-DOC-10`), **каркас слоёв** в `libs/pdr-core` (`PDR-ARCH-01`), **типы
платформы** — идентификаторы, время, доменные ошибки, порты часов и генератора
идентификаторов, фейки к ним в `libs/pdr-testing` (`PDR-ARCH-06`),
**модули четырёх контекстов первой фазы** с общим реестром событий и двумя
проверками границ (`PDR-ARCH-03`, `PDR-ARCH-07`), **девять решений** в
[`docs/adr/`](docs/adr/) (`PDR-DOC-02`, `PDR-DOC-09`) и **локальный запуск**:
один compose, профили переменными, `make up` (`PDR-INF-01`). Ни TypeScript, ни
SQL в репозитории пока нет.

Живого продакшена у проекта нет, и это осознанное решение: инфраструктура не
притворяется, что он есть.

### Одна команда

```sh
cmake -S . -B build && cmake --build build
```

Нужны CMake не ниже 3.25 и компилятор с C++20; больше ничего ставить не надо.
Соберутся две цели — `pdr_core` (домен) и `pdr_application` (сценарии): они не
зависят ни от одной внешней библиотеки, и это проверяется каждой сборкой.
Третья цель, `pdr_infrastructure`, появляется только если в окружении найден
userver; без него конфигурация честно сообщает, что цель пропущена.

Корневой `CMakeLists.txt` подключает подкаталог `libs/` или `services/` в тот
момент, когда в нём появляется собственный `CMakeLists.txt`.

Тесты идут за секунды, им не нужны ни база, ни докер, ни сеть:

```sh
ctest --test-dir build --output-on-failure
```

Границы проверяются отдельно и тоже за секунды — слои и контексты по
директивам `#include`, владение таблицами по карте контекстов:

```sh
python3 scripts/check_layers.py
python3 scripts/check_table_owners.py
```

Локальная установка поднимается одной командой — база и заглушка инференса:

```sh
cp deploy/env/local.env.example deploy/env/local.env   # и поменяйте пароль
make up
```

Что именно поднимается, почему compose ровно один и чего в нём намеренно нет —
[deploy/README.md](deploy/README.md). Живого прода нет, и это не заготовка под
него.

Сервисов приложения среди поднятого пока нет:

* в `services/` нет ни одного сервиса — они появятся по одному, вместе со своей
  фазой;
* `db/migrations` пуст — миграций нет, и `make migrate` честно об этом говорит;
* `clients/web` пуст — ни `package.json`, ни зависимостей, ни dev-сервера.

## Дерево

```

libs/pdr-core/src/            платформа: то, чем пользуются все контексты

    application/              порты — абстрактные интерфейсы: часы, генератор id
    infrastructure/           адаптеры: настоящие часы и генератор идентификаторов

    contract/                 единственный заголовок, видимый соседям
    src/                      всё остальное — соседям не видно
```

### Два имени в дереве, которые стоит объяснить

**`clients/`, а не `front/`.** Множественное число выбрано заранее: мобильные
приложения — принятое продолжение проекта, а переименовывать каталог на живой
истории дороже, чем назвать его правильно сразу. Монорепозиторий здесь не по
привычке: web и mobile делят типы, сгенерированные из OpenAPI, и токены
дизайна. В разных репозиториях это означало бы версионирование и публикацию
пакета на каждое изменение схемы — и клиенты неизбежно разъехались бы по
версиям API.

**`ml/` — тоже C++.** Это инференс готовых моделей, и его закрывают
ONNX Runtime, llama.cpp и нативный Vosk. Питон живёт только в `ml/export/`
и только для разового превращения модели в ONNX — это шаг сборки, а не
рантайм. Однородность стека сохраняется.

## Стек

Бэкенд — C++ и userver. Хранилище — PostgreSQL, единственное: очереди на
`SKIP LOCKED`, векторный поиск на pgvector, отдельной инфраструктуры под них
не заводится. Клиент — TypeScript, React, Vite. Сборка — CMake и Docker,
CI — GitHub Actions.

## Правила, принятые до первой строки кода

Они уже действуют — но машинных проверок для них в дереве пока нет, проверки
приходят вместе с кодом, который они стерегут.

**Слои.** `core` не знает ничего, `application` знает `core`,
`infrastructure` знает обоих. Зависимости направлены только внутрь. Часы и
генератор идентификаторов — такие же порты, как база: иначе тесты станут
флаки. Порты узкие: `BookingRepository`, а не универсальный `Repository`.
Каждый ограниченный контекст — отдельный модуль, перекрёстный импорт между
модулями контекстов запрещён.

**Данные.** `tenant_id` на каждой доменной таблице и RLS: изоляция
структурная, а не дисциплиной. Время — `timestamptz` в UTC плюс отдельная
колонка с зоной IANA; локального времени без зоны не хранится нигде. Деньги —
целые минорные единицы и код валюты, ни одного числа с плавающей точкой.

**Внешний мир.** Данные карт не проходят через бэкенд никогда, даже транзитом.
`Idempotency-Key` обязателен на всех мутирующих запросах. Ошибки — problem+json
(RFC 9457) с идентификатором запроса, отображение доменных ошибок в HTTP живёт
в одном месте. Секреты падают на старте, если их нет: значений по умолчанию не
существует. Внешние API — только за портом и минимум в двух реализациях,
настоящей и заглушке.

**Интерфейс.** Значения системы дизайна берутся только из
`clients/shared/design/tokens.json`. Продукт выглядит одинаково для всех:
ни «детского», ни «профессионального» вида не существует — различаются права
и содержимое, но не оформление.

**Сквозной принцип.** Факты считаем детерминированно, смыслы отдаём модели,
решение оставляем репетитору. Модель не может подменить рассчитанное число.

## Документация

Каталоги ниже созданы и пусты — файлы появятся вместе с задачами, которые их
заводят.

* [`docs/adr/`](docs/adr/) — принятые решения и их причины: на чём стоим
  (C++ и userver, только PostgreSQL, арендатор с первого дня, никакого
  фиктивного прода, монорепозиторий с клиентами) и что берём снаружи
  (видео — готовое, оплата — порт с первым адаптером, продавец — репетитор,
  родительский доступ — с первой версии). У каждого решения назван отвергнутый
  вариант — иначе это не решение, а описание.
* [`docs/architecture/`](docs/architecture/) — контексты, слои, потоки данных:
  [`layers.md`](docs/architecture/layers.md) — вертикальная граница (слои),
  [`context-map.md`](docs/architecture/context-map.md) — горизонтальная
  (контексты, владение таблицами, группировка в процессы),
  [`new-context.md`](docs/architecture/new-context.md) — чеклист заведения
  нового контекста.
* [`docs/api/`](docs/api/) — OpenAPI, источник типов для клиентов.
* [`docs/product/`](docs/product/) — правила продукта и интерфейса; двадцать
  девять правил интерфейса и опыта лягут в `docs/product/rules.md`
  (`PDR-UI-01`), и у каждого будет машинная проверка: правило без проверки не
  считается введённым.
* [`docs/runbooks/`](docs/runbooks/) — действия при инцидентах.
* [`docs/legal/`](docs/legal/) — оферта, персональные данные, чеки.

Два документа написаны раньше кода и читаются прямо сейчас:

* [`docs/ROADMAP.md`](docs/ROADMAP.md) — направления и, главное, то, чего мы
  делать не будем, с причиной у каждого пункта.
* [`CONTRIBUTING.md`](CONTRIBUTING.md) — идентификаторы задач, формат коммитов
  и правила, которые обязана соблюдать каждая задача.

Отдельного реестра задач в репозитории нет: история — это `git log`.

## Тесты

Unit-тесты ядра и сценариев запускаются через `ctest` и работают против фейков
из `libs/pdr-testing`: без базы, без докера, без сети, за миллисекунды.
Отрицательные случаи обязательны везде, где они названы, — в том числе такие,
которые ОБЯЗАНЫ не собираться: перепутанные типы идентификаторов проверяются
целями `core.compile_fail.*`, а сама проверка слоёв — своим
`python3 scripts/check_layers.py --selftest`.

Полноценный фреймворк тестов (фикстуры, параметризация) заводится отдельной
задачей области TST; сейчас тест — обычная программа с кодом возврата. Договор
на остальное такой: contract-набор гоняется дважды — на фейке и на настоящем
адаптере; интеграционные — только сквозные сценарии.
